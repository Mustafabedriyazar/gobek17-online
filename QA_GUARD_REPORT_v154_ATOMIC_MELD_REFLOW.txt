1. USER-REPORTED VISUAL DEFECT
============================================================
Observed case matches a layout-tier boundary in the owner's per area.
Representative state: one 5-tile meld + two 4-tile melds; process a 6th tile into the first meld.

v153 root reproduction at 1536x712:
- before feed tile tier: 47x65
- after feed tile tier: 40x56
- width/height snapped immediately
- left/top still had 160 ms CSS transition
- immediate screen-space pitches inside the 6-tile meld:
  34.0703125, 34.0703125, 34.0703125, 34.0703125, 9.734375
- final settled pitch after transition:
  29.203125 uniformly

The last tile therefore appeared on top of / too close to its neighbor during the first frame. Low-FPS Android made the defect visually much more obvious.

============================================================
2. ROOT CAUSE
============================================================
Real engine-owned meld nodes inherited global .tr left/top transitions.
When flowZone() changed size tier or row after PROCESS:
- size changed immediately,
- old tiles' positions interpolated from stale geometry,
- newly created processed tile appeared at final geometry,
- plate geometry also used final bounds immediately.

This created a temporary mixed-geometry meld despite engine state being correct.
The old meldVisualAudit could not detect it because inline target left/top values were already correct; getBoundingClientRect was still mid-transition.

============================================================
3. v154 FIX
============================================================
canonicalizeMeldTile() now pins:
  transition: none !important
for real .tr.mld nodes in addition to the existing transform/translate/rotate/scale pins.

Result:
- flowZone remains the single geometry authority,
- all real meld tiles snap atomically to final left/top/width/height,
- process animation remains on motion-flight clones only,
- no gameplay mutation was introduced,
- no forced FREE-board fallback or meld split was added.
